# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An R analytics project for Sleeper fantasy football, grown from the "DDBM" redraft league. It began as one-off scripts that pull the public Sleeper API and render `DDBM*.png` charts, and now also ships a reusable **`sleepermetrics`** package + Shiny dashboard that generalise the same analytics to *any* league.

Components (roughly oldest to newest; the scripts are the origin, the package is the productized form):
- **`ddbmFF.R`** the **origin source / historical basis**: single-season analytics (one season's matchups/rosters/transactions to ~26 charts in `results/<season>/`). Run interactively in RStudio (`FantasyFootball.Rproj`) or headless via `Rscript`. **Left untouched**; its chart set has been *ported into and improved within* `R/sleepermetrics` + `python/sleepermetrics`. Ported (all parity-verified, mirrored R↔Python): roster/position analytics (`sl_position_scoring`/`sl_roster`/`sl_starter_bench`), weekly table-position bump line (`sl_table_position`), stacked weekly team points (`sl_plot_team_points`), average position-points box (`sl_plot_position_box`), average roster composition (`sl_roster_counts`), and the transaction-based **trade** and **waiver/FA** performance charts (`sl_trade_performance`/`sl_waiver_performance`), the last two backed by a `transactions` layer now assembled into the `season` object. The trade/waiver metrics improve on the origin: "points while rostered" is read straight from `pl_wk` roster membership (join on `player_id` for trades so both teams show; on `player_id`+`roster_id` for waivers) rather than the origin's fragile transaction-stint reconstruction. Only the team×user treemap variant is intentionally not ported (superseded by `sl_position_scoring` + the roster heatmap).
- **`leagueAnalytics.R`**: cross-season *career* analytics. Walks the whole season chain and aggregates by persistent `user_id` (same manager across seasons despite changing display names/rosters), writing `results/league/` (career standings, finish trajectory, points-per-season, manager-player loyalty, plus `league-career-summary.md` + `.csv`). Reuses the hardened `callSleeper`/`ensure_cols`/`buildLeagueChain`/NA-matchup logic from `ddbmFF.R`.
- **`R/sleepermetrics/`**: a proper R package (the general, canonical implementation), living inside the `R/` instance dir to mirror `python/`. Roles are segmented into files: `api.R` (`sleeper_api`), `players.R`, `league.R`, `season.R` (assembles a `sleeper_season` S3 object: `team_wk`/`pl_wk`/`lineup`/`standings`/`user_map`/`transactions`/`accounts`, plus the roster-aware optimal-lineup solver and the transactions unnester `sl_unnest_transactions`), `metrics.R` + `weekly.R` (compute to tibbles), `plots.R` (render to ggplot), `summaries.R` (narrate to markdown), `dashboard.R` (Shiny), `discord.R` (Discord). Public API is prefixed `sl_` (e.g. `sl_season()`, `sl_luck()`, `sl_plot_efficiency()`, `sl_summary_season()`, `sl_dashboard()`). Has roxygen docs, a `NAMESPACE`, and network-free `testthat` tests. Load with `pkgload::load_all("R/sleepermetrics")`.
  - **Discord** (`discord.R` + `inst/discordbot/`): `sl_post_weekly()` posts a weekly recap (highlights + scoreboard + charts) to a channel **webhook** (schedulable, no hosting); `sl_discord_serve()` runs a **plumber** interactions endpoint answering slash commands (`/standings`, `/luck`, `/weekly`, `/career`, …); it verifies Discord's Ed25519 signatures via `sodium` (`sl_discord_verify`) and defers each command, delivering the chart/summary as a follow-up. `sl_discord_register_commands()` registers the commands. Needs `plumber`, `sodium`, `curl` (Suggests); the endpoint needs a public HTTPS URL.
- **`app.R` + `R/ddbmMetrics.R`**: the **prototype** Shiny dashboard the package was generalised from (still runnable). The package's bundled app (`R/sleepermetrics/inst/shinyapp/app.R`, launched via `sl_dashboard()`) supersedes it; both hit the same metrics. The optimal-lineup solver in both reads each league's `roster_positions`, so FLEX/SUPER_FLEX/etc. adapt per league.
- **`python/`**: a **parallel Python port** of the metrics engine + Discord bot (a venv-based instance, verified to produce output identical to the R package). Same module segmentation (`sleepermetrics/{api,players,league,season,metrics,weekly,plots,summaries,discord_bot}.py`), `pandas` frames instead of tibbles, `matplotlib` charts mirroring `theme_sleeper`, and a **discord.py** slash-command bot (gateway, no signature/HTTPS needed, unlike the R plumber endpoint). CLI: `python/bot.py {weekly,serve}`; `pytest` tests in `python/tests/`.
- **`launch.py`** (repo base): the **single access point** that starts the Discord bot for either instance: `python launch.py <serve|weekly|dashboard|report> [--r|--python] [args]`. The
instance is a **flag, defaulting to Python**; `--r` selects the R instance, and the
flag may sit before or after the mode. It shells to `python/bot.py` (via `python/venv`) or `R/run_bot.R` (which `pkgload::load_all`s `R/sleepermetrics`; the `R/` dir also holds the legacy `ddbmMetrics.R` prototype). Per-instance config lives in `python/.env` and `R/.env` (templates: `*.env.example`); both default to the DDBM league. Note Windows is case-insensitive so `R/` == `r/`; the tracked directory is `R/`.
- **`season/` + `scoring.R`/`scoring.py` + `playoffs.R`/`playoffs.py`**: a **custom playoff engine** for leagues whose playoff is run *outside* Sleeper (DDBM 2025: custom week range, and lineups submitted to the commissioner because Sleeper's rosters were locked). Sleeper can only express its own bracket, and for 2025 its stored `winners_bracket` is genuinely incoherent (the team it records as losing rounds 1 *and* 2 is also the recorded `p == 1` champion), so the bracket shape must come from config, not the API. **Points are recomputed from first principles**: each submitted starter is priced from raw weekly stat lines (`/stats/nfl/regular/{season}/{week}`) times the league's **point-calculation chart** (`scoring_settings`): `sl_scoring_chart()`, `sl_score_lineup()`. This is verified exact: it reproduces Sleeper's own player points (175/175 in wk15) and, replaying Sleeper's own bracket, all 12 matchup winners + the champion with zero mismatches. `sl_playoff(config)` resolves a bracket round by round; only **roster inputs** per matchup are required; winners advance via `"W:<matchup_id>"` refs, `bye` passes a team through, multi-week rounds sum, undecided/unsubmitted matchups report `PENDING` (so it is safe to run live), and lineups are slot-checked (`sl_check_lineup()`). The chart is snapshotted into the config so finished brackets stay reproducible. Wherever a chart is *displayed*, it is translated out of Sleeper's stat codes into plain English by `statnames.R`/`statnames.py` (`sl_scoring_readable()` / `sm.scoring_readable()`), grouped (Passing/Rushing/…/Points allowed), each weight phrased as a sentence (`pass_yd: 0.04` becomes "1 point per 25 yards"; a fractional *non-yardage* weight stays per-event, so `pass_sack: -0.5` becomes "-0.5 points", never "-1 point per 2"), reading order taken from the dictionary rather than alphabetically (so points-allowed brackets descend), and unknown keys surfaced in an "Other" group instead of being dropped. The dictionary is parity-exported, so the R and Python vocabularies cannot drift. Charts: `sl_plot_playoff_bracket()`, `sl_plot_playoff_matchup()`; live in the dashboard's **Playoffs** tab (`sl_dashboard(playoffs = "season")`). Note `last_scored_leg` caps the `season` object at wk17, but wk18 stats *are* fetchable; the playoff engine reads stats directly, so it spans weeks the season object cannot. **A round's `starters` are the commissioner's submitted lineups and are not derivable from Sleeper**: rosters were locked, so they do not match any Sleeper matchup and no roster-membership check should be added. The 2025 `R4M1` shipped as a stale copy of `R3M1` (same nine ids bar one) which scored plausibly but wrongly, so each matchup now carries a `_slots` line naming its picks in slot order; nine opaque ids make that failure mode invisible. Corrected against the commissioner's sheet: LuckyHarm 132.40, SimonSmith 124.53 (champion unchanged; margin went from a 50.88 rout to 7.87). **Bracket configs live one level down, under `season/<league_id>/<season>.json`** (a Sleeper league id is unique per season, so this also disambiguates two different leagues sharing a season number); `config_paths()`/`sl_playoff_configs()` walk it, keeping only numeric-named subfolders, so `season/adp/` (below) and `season/fixtures/` are transparently skipped. Both engines resolve the whole `season/` root from one env var, `SLEEPERMETRICS_SEASON_DIR` (default `<repo>/season`). See `season/README.md`.
- **`season/adp/`: the Python Draft tab's ADP cache.** `sleepermetrics.draft.redraft_board_adp()` simulates a redraft ordered by Sleeper's own **ADP** (average draft position) instead of true season value ("what the field at large would have drafted", the counterpart to `redraft_board()`'s "what a draft knowing the results would have looked like"). ADP itself comes from an **undocumented** Sleeper endpoint (`api.sleeper.com/projections/nfl/<season>`, reverse-engineered, not part of the documented v1 API `api.py` otherwise wraps), fetched live and, on success, written to `season/adp/<season>.json` so a later offline run (or a future run after Sleeper changes/removes the endpoint) still has the latest successfully-captured snapshot to fall back to. Deliberately **season-scoped, not league-scoped** like the playoff configs above (Sleeper publishes one ADP set per year for the whole platform), so it lives in its own shared subfolder rather than being duplicated into every league's own files. The ADP *format* (`adp_std`/`adp_half_ppr`/`adp_ppr`/`adp_2qb`) is picked per-league from the league's actual `rec` scoring weight and QB slot count (`_adp_field_for`), not assumed. Python-only for now, same precedent as this module's other newer draft analytics below.
- **`verify.py` + `parity/`**: the cross-language test harness. `python verify.py [league_id]` runs the Python `pytest` suite, the R `testthat` suite, then both exporters (`parity/export_{py,r}.py/R`) which emit an identical canonical metric JSON, and diffs them field-by-field (numbers within tolerance, summary text exact). Exit 0 only if all pass. This is how R↔Python parity is enforced; run it after changing either implementation.

## Running

Two ways to run:
- **RStudio (the author's way):** open `FantasyFootball.Rproj` and source/step through `ddbmFF.R` top to bottom. Most analysis blocks have a trailing `# view(...)` comment naming the frame to inspect with RStudio's `View()`.
- **Headless:** `Rscript ddbmFF.R` from the repo root works end to end (verified). Select a season with the `DDBM_SEASON` env var, e.g. `DDBM_SEASON=2024 Rscript ddbmFF.R`; unset/empty uses the most recent season. In RStudio instead set `targetSeason <- "2024"` in the Config block (`NULL` = current).
- **Dashboard:** `shiny::runApp(".")` (or `Rscript -e 'shiny::runApp(".", port=8100)'`) launches the web app; open the printed `http://127.0.0.1:<port>`. It auto-loads the default DDBM league on startup; type any league ID and click **Load league** to switch. Needs `shiny`, `bslib`, `DT`, `ragg` (and `nflplotR` for the demo flair). Note: `runApp` blocks and reads the source once at startup; after editing `app.R`/`R/ddbmMetrics.R` you must stop and relaunch. Verify metric logic **headless** by sourcing `R/ddbmMetrics.R` and calling the functions directly (no app needed); that's the fast path.

Notes:
- The package install lines at the top of `ddbmFF.R` are commented out; install them once into your R library before first run (notably `tidyverse`, `httr2`, `ggplot2`, `treemapify`, `tidytext`, `patchwork`, `RColorBrewer`, and the `nflverse` family).
- `getSleeperPlayers.ps1` is a standalone PowerShell helper that downloads the full Sleeper player dump to a JSON file; it is not called by the R script and writes to a hardcoded absolute path under `~/Documents/Data/FantasyFootball`.

Each chart block ends in a `ggsave(out("DDBM*.png"), ...)`, where `out()` resolves to `results/<season>/`. Chart PNGs are gitignored build artifacts (regenerate by running the script); only `results/<season>/player-patch-log.md` is tracked.

## Data flow / architecture

`ddbmFF.R` is the whole program. It runs in four stages:

0. **Config (season selection).** Near the top, after the `/state/nfl` fetch, a Config block sets `currentLeagueId` (head of the chain) and `targetSeason`. Sleeper stores each season as a *separate* league object chained backwards by `previous_league_id`, so `buildLeagueChain()` walks that chain into a `season -> {league_id, last_scored_leg}` map. The selected `season` (default = most recent) resolves `leagueId`, `lastWeek` (= that season's `last_scored_leg`, the correct loop cap; see "Things that will bite you"), and `outDir`/`out()` for `results/<season>/` output.

1. **General Sleeper data**: `callSleeper(objectId, endpoint)` wraps `https://api.sleeper.app/v1`. Player metadata is the largest payload, so it is cached to `sleeperPlayerData.rds` and only re-fetched when the file's mtime is not today (see the `fileDate == today` guard). The raw nested player list is flattened into `playerDF`, then into two lookups: `playerMap` (team-filtered, `player_id -> name/position/team`, used where "currently on a team" matters) and **`playerInfo`** (team-INDEPENDENT `player_id -> name/position`, used for all name/position joins so released/team-less players resolve without manual patches).

2. **League-specific data**: keyed off `leagueId` (from the Config block, not a hardcoded literal). Rosters and users are merged into `userMap` (`roster_id -> user_name`). The script then loops `1:lastWeek` over `/matchups/{week}` and `/transactions/{week}` to build the three central frames everything downstream depends on:
   - `matchupResults`: one row per team per week with cumulative W/L, points, and computed league `table_position`.
   - `DDBMRosters`: one row per player per team per week, with `position`, `player_points`, and `is_starter`. This is the workhorse frame.
   - `allTransactionsDF`: adds/drops/trades unnested to one row per player movement.

   After `DDBMRosters` is built, `applyPlayerPatches()` applies any `seasonPatches[[season]]` (an id-keyed `tribble`, normally empty; `playerInfo` resolves almost everything) and a per-season patch log is written to `results/<season>/player-patch-log.md`.

3. **Analysis + charts**: built from the `Filter*` versions of those frames (`FilterDDBMRosters`, `FilterMatchupResults`, etc.). Because the week loops only cover scored weeks (`1:lastWeek`), the `Filter*` frames no longer drop a week; they just set the `position` factor ordering. Derived frames (`*OfTheWeek`, `playerRosterPerformances`, `playerTradePerformances`, `playerWaiverPerformances`, roster/position breakdowns) feed the `ggplot` blocks.

## Things that will bite you

- **Week cap = `last_scored_leg`, not `state.week`.** The week loops are capped by `lastWeek`, taken from the league object's `settings.last_scored_leg` (the last fully-scored week, e.g. 17 for 2025; 16 for 2024). Do **not** swap this for `currentSeason$week` (`/state/nfl`): that value collapses to `0` in the offseason (which breaks `1:lastWeek`) and is phase-dependent. `last_scored_leg` is live-safe and per-season. (Historical note: this replaced an earlier hardcoded `currentWeek`/`latestWeek = 18` plus a `-1` exclusion filter.)
- **Player resolution / patches are id-keyed now.** Name/position come from `playerInfo` (team-independent), so released/team-less players resolve automatically; there are no more fragile `DDBMRosters[<row>, ...]` row-index patches. If a player is *genuinely* missing from the Sleeper player DB, add an id-keyed row to `seasonPatches[[season]]`; the run-generated `results/<season>/player-patch-log.md` lists any unresolved `player_id`s. The old row-index comments (e.g. `row 1872 -> 1672`) are retained in `ddbmFF.R` purely as a historical changelog; they are intentional, not stale; preserve them.
- **Playoff weeks have teams with `matchup_id = NA`** (eliminated/bye). The matchup self-join uses `na_matches = "never"` so those teams are *not* paired against each other; they get a single no-result row, and the cumulative record uses `cumsum(coalesce(result == "W", FALSE))` so a no-game week doesn't poison the standings. Removing this guard reintroduces phantom playoff matchups (it silently corrupted records for eliminated teams in every season, e.g. 2025 rezzu was 5-12, corrected to 3-12).
- **Seasons vary in shape; keep it tolerant.** Across the season chain the league has different team counts (2022/2024 = 6 teams, 2023 = 8, 2025 = 10) and different transaction/user column sets. Drop-selects use `-any_of(...)` and `ensure_cols()` backfills missing metadata/settings columns, so don't reintroduce bare `select(-col)` or `select(where(~ !any(is.na(.))))` for optional fields (the latter dropped `team_name` whenever any user left it blank). The per-team chart loop iterates the season's actual users, so a season simply renders fewer per-team charts.
- **Accounts / avatars (`sl_league_accounts()` / `sm.league_accounts()`).** Per-account identity, team name + icons, lives in the season's `accounts` frame, deliberately **separate from `user_map`**: `user_map` is joined into `team_wk`, so any column added there rides along into every metric. The two Sleeper avatar fields have **different shapes** and are easy to confuse: a user's `avatar` is a bare id needing the CDN prefix (`https://sleepercdn.com/avatars/<id>`), while the league-specific `metadata.avatar` (custom team picture) is *already a full url*; `sl_avatar_url()` handles both, so never hand-build one. Career identity keys on the persistent `user_id` (names change between seasons) and takes the **most recent** season's name/icon. In Python, remember pandas `NaN` is **truthy** in Jinja; convert to `None` before templating or a missing avatar renders `src="nan"` (see the `records()` bullet).
- **Season report (`sl_season_report` / `sm.season_report`, `report.R`/`report.py`).** The **export deliverable** (the slothstats-style "clean report"): one **self-contained HTML file** bundling the narrative, six KPI tiles, a per-manager table, and ~19 charts, each **embedded as a base64 PNG data URI** so there are zero external assets; it emails, drops in a drive, and opens offline. The dashboards are for exploring; this is for keeping. **CSS + template are byte-identical between R and Python** so both instances emit a visually matching report (theme-aware light/dark via `prefers-color-scheme` + `data-theme`); the per-team table values are diffed R↔Python. It is **presentation, not parity-gated** (the harness doesn't diff the HTML), but every number in it flows from the parity-checked metrics. Chart embedding is **best-effort**: a panel that errors (or has no data) is skipped, never fatal; R must guard `sl_trade_performance`/`sl_waiver_performance` inside that skip because a *column-less* empty frame (only the test fixture; real data is always typed) errors in the `nrow()` pre-check. R needs `base64enc` (`dataURI()`); portraits still honour `SLEEPERMETRICS_NO_IMAGES`. Access: `python launch.py report [league] [--season Y] [--out f.html] [--all] [--r]` (runners `python/make_report.py`, `R/make_report.R`), the **Season report tab** in the FastAPI app, the **/report** route (the standalone file; `download=1` sends it as an attachment), and a **Download season report** button (`downloadHandler`) in Shiny.
- **Report content is one spec, two renderers (Python).** `report_parts()` returns the report as *data*: headings, tiles, narrative, lead table, and ordered sections where each section carries pre-built `html` (the manager tables), `charts` as `(chart_key, caption)`, or **both**. The week-by-week section is a game log followed by its charts, so neither renderer may treat `html` as excluding `charts` (`_section()` omits its `<h2>` when handed an empty title, which is how the combined section avoids a repeated heading). `season_report()` bakes those keys to base64 PNGs (the standalone file); the **web app's report tab renders the same spec natively**: tables inline, charts as ordinary `/chart/<key>` `<img>`, which is why the tab's charts stream in with the shared skeleton **and follow the dashboard theme** (the old iframe embed baked them light forever). A chart's **kind** decides what it is called with: `_chart_args()` maps `"season"` / `"seasons"` / `"playoff"` / `"season+manager"`, and a kind whose input this report lacks drops the panel rather than erroring. The chart keys in `_CHART_FNS` must stay in step with the app's `/chart` endpoint, and a `"season+manager"` key additionally needs an entry in the app's `MANAGER_CHARTS` **and** `manager` forwarded on the img url (`|urlencode`, since a name with a space or `&` otherwise breaks the query string), or it renders in the standalone file but 404s in the tab. Don't put a `<script>` in the standalone file; a test asserts it stays script-free, so all report interactivity is native `<details>`.
- **Trade direction is NOT recoverable from `trade_performance`.** That metric joins on `player_id` **alone**, deliberately, so both sides of a deal appear on the league-wide chart. Filtering it by `user_name` therefore returns players a manager traded **away** as well as those they acquired, and a player's pre-trade points make them look like that manager's best *add* (this shipped: Bijan Robinson, traded away in wk12, was reported as LuckyHarm's best trade add). Direction only survives in `s.transactions`; use `_mgr_trade_ids(s, rid, "add"|"drop")`. Second trap in the same place: rank and display **`points`** (this manager's points while rostering the player), never **`total`** (the player's points across *every* roster that held him): `total` both picks the wrong row and overstates the figure, and it was silently corrupting the waiver "best pickup" too, where direction was already fine.
- **Transaction ledgers (`metrics.trade_ledger` / `waiver_ledger`, webapp-only).** The Transactions tab's detail tables, and the shape the per-manager report's "Trades & the waiver wire" section uses. They keep the **deal** intact, grouped by `transaction_id`, one row per team in it, rather than reducing to per-player rows. `net` = what the incoming players scored *for this team* minus what the outgoing ones scored *for whoever received them*, with each player's points attributed to the roster that actually took him (so three-way trades work; the sanity check is that a season's nets sum to zero). Waiver rows are collapsed to unique (manager, player) with `times` for churn; points are already a per-(player, roster) total, so a row per add would repeat the same figure and read as two separate hits. **`trade_deals()`** folds the ledger's per-team rows into one entry per deal for display: each side lists only what that team *received*, so a player is named once under whoever got him instead of appearing on both a "received" and a "gave up" row. A deal under 10 points net is reported as "a wash" rather than crowning anybody on noise.
- **Coaching + roster detail (webapp-only, `metrics.coaching_detail` / `bench_regrets` / `roster_detail` / `roster_weeks` + their `*_standouts`).** The tab drill-downs behind the efficiency and position charts. **`bench_regrets`** is the sharp one: per team-week it finds the benched player who most outscored a **same-position** starter (so the swap was legal at the time) and marks `flipped` when that single change would have turned the loss into a win; every flip is re-derivable from `team_wk` + `pl_wk`, and that is the check to run if the logic is ever touched. It considers only the single best swap per week, not combinations, which is what keeps "this one decision lost the game" defensible. `coaching_detail`'s `eff` must stay equal to the parity-checked `efficiency` metric; cross-check it rather than assuming. `roster_detail`'s `bench_pts` is the cost of the *roster carried*, deliberately distinct from lineup efficiency (the cost of the *decision*).
- **"Did they keep him?" is roster membership at `last_week`, not transaction order.** Used by the report's waiver drill and the draft tab. A cut followed by a re-add is churn, not an exit, so comparing a drop week against an add week is wrong; and an add and a drop in the **same week** cannot be sequenced from week numbers at all (both bit). `pl_wk` membership in the final scored week is ground truth and covers drops, trades and same-week churn alike.
- **Per-manager report scope (`manager=`).** Scopes the whole report to one team: manager tiles, a manager narrative, a standings *neighbourhood* (leader to their cluster to last) + a per-category rank table, then sections that are about **them**: week-by-week game log, position mix, season standouts, draft class, rivalries, splits/awards, their own postseason run and their own career. It deliberately does **not** restate the league-wide charts. A manager the selected season doesn't have falls back to the whole-league report rather than erroring.
- **Drill-downs are per-row, never a "show the whole table" toggle** (`_drill_table`): a grid-aligned `<summary>` row that expands into `_facts()` labelled fields and/or `_mini_table()` mini-tables, never a run-on sentence. Ranks render as `_rank_pill()` badges (top third good / bottom third bad) and a manager who *is* the league best/worst in a category gets their name flagged in that column. Both the standalone `_CSS` and the app's `.reportpanel` block in `style.css` must carry these classes; the markup is shared, so a style added in one place only is half-broken in the other.
- **`optimal_lineup()` (season.py)** returns the best legal lineup's *players* tagged with the slot each fills; `optimal_points()` is now just its sum. It feeds the week drill's "Started vs Optimal" comparison. This is a **parity-sensitive path** (`lineup.optimal` feeding the diffed `efficiency` metric), so any change to the selection logic must keep totals identical; re-check with `verify.py`.
- **Lineup *display* order is separate from lineup *fill* order (`SLOT_ORDER` / `assign_slots()` / `slot_sort_key()`, season.py).** Every roster table in the report reads in scoreboard order: `QB, RB1, RB2, WR1, WR2, TE, FLEX, K, DEF`. That is **not** `POSITIONS` order, and deliberately not `optimal_lineup()`'s fill order either: the solver fills every fixed position (K and DEF included) *before* any flex, which is correct for selection but strands FLEX at the end of the list. `assign_slots()` is the counterpart to the solver: it takes a lineup **as given** and works out which slot each player occupies (fixed positions first, then flex from whoever is left, highest scorer first so RB1 outscores RB2), numbering repeats. Use it for anything displayed: the week drill's Started **and** Optimal tables (re-labelling the solver's own picks so the two align row for row; the player set and total are untouched, so parity is unaffected) and both playoff-round lineups. Sleeper's slot ordering is **not** available to recover from: `assemble_season` stores `starters` as a **set**, discarding it. Anyone who fits no slot is appended, never dropped, and a league with no slot config degrades to plain position labels.
- **Sortable tables + cache-busting (web app).** Any `#panel table` sorts by clicking a column header (`index.html`), keying on the first embedded number when every cell has one (`#3 of 10` becomes 3, `9-8` becomes 9, `+41.4` becomes 41.4) and alphabetically otherwise; the draft board opts out via `nosort` (it's a round × slot grid), and tables containing the neighbourhood's `⋯` gap rows skip sorting automatically. `style.css` is linked with `?v=<mtime>` (`asset_v()`) because a **stale cached stylesheet** silently strips the report's grid layout into run-together text; that symptom bit three times before this fix. **A row can carry MULTIPLE `.detail-row` siblings, not just one** (a per-row drilldown that expands into several sub-rows, e.g. the Draft-finds `×N teams` per-team breakdown, one `.detail-row` per team): `makeSortable` groups a trigger row with EVERY immediately-following `.detail-row` so a re-sort moves the whole group together, keyed on the group's leading row, and `prepFaRows` toggles all of them as one unit. Ported from `weekly_report.html`'s own single-sibling version of this same pattern (which had already drifted ahead of the dashboard's shared copy) and extended to the multi-sibling case; check both copies stay in sync if either is touched again.
- **Composite / behavioural metrics (`sl_allplay` / `sl_power_rank` / `sl_manager_profile`).** Three ffwrapped-style additions computed entirely from frames already assembled, no projections or external data. **All-play** surfaces the schedule-independent standings (`allplay_w`/`allplay_l` were already summed into `standings`); `rank_delta = allplay_rank - final_position`, so **positive means the real schedule flattered the team** (finished better than merit) and negative means it robbed them. **Power rank** is a z-scored blend (points 0.35 / all-play 0.30 / recent-form 0.20 / efficiency 0.15); the composite is a *mean/sd-derived* column, so it is **returned unrounded and rounded only at display/export**, per the parity discipline (rounding it inside the metric reintroduces the `.x5` R↔Python tie). **Manager profile** aggregates `transactions` + `lineup` into moves/trades/drops/`lineup_iq`; its `tally()` helper must **defer column access** (a season with zero moves has a column-less empty transactions frame; touching `tx["type"]` before the length guard is a KeyError in Python / handled by NULL in R). Charts live on the **overview** tab (all-play + power) and **transactions** tab (manager profile) in both dashboards.
- **Manager avatars on the team charts (`headshots.R` / `headshots.py` + the `.sl_row_avatars`/`.sl_scatter_avatars` and `_row_avatars`/`_point_avatars` helpers).** Every chart whose rows/points are *teams* (standings, power rank, all-play, efficiency, luck, manager tendencies, PF-vs-PA) hangs the manager's account avatar beside their name, the same identity the Career tab's Managers panel shows, keyed on `user_name` via the season's `accounts` frame (`avatar_url`, falling back to `team_avatar_url`). Same best-effort contract as the player portraits: no avatar / no network gives a plain text label, misses cached, `SLEEPERMETRICS_NO_IMAGES=1` disables. Rows read **`[icon] name  |  bar`**, icon first, like the Managers panel, via one shared identity-axis helper (`.sl_identity_axis` / `_identity_rows`) used by **both** the team and player charts. It keeps the names as real axis text (so the column stays auto-sized) but **left-aligns** them, then hangs the token immediately left of that column: R offsets by `grid::grobWidth()` of the longest label (resolved at *draw* time, so no guessing) and adds a fixed `plot.margin`, while Python draws once and **measures** the rendered label extents. Traps, all of which bit and are now guarded: (1) the **full `/avatars/<id>` url is served as `application/octet-stream`** (~400KB) which the `image/*` guard rejects; use the **`/avatars/thumbs/<id>`** form (a ~15KB `image/png`), which is what a chart token wants anyway; (2) the width used to step the icon back must match what the axis text ACTUALLY renders at: `theme_sleeper()`'s `%+replace%` swaps `axis.text` out wholesale, dropping `theme_minimal`'s `size = rel(0.8)`, so labels inherit the **13pt base size**, not 10.4, and measuring at 10.4 put the icons on top of the names; (3) in R the effective tick element is **`axis.text.y.left`, not `axis.text.y`**: the complete theme defines the `.left` child, which shadows the parent, so setting `axis.text.y` renders *byte-identically* and the gap for the token never opens (and the decoration must be added **after** `theme_sleeper()`, since a complete theme replaces everything before it); (4) `urls[[name]]` on a named atomic vector **errors** on a missing name instead of returning `NULL`, so a season with no `accounts` blew every team chart up; check `%in% names()` first (same trap as `paths[[key]]` in `sl_apply_playoffs`). Avatars are a pure overlay, so parity is unaffected.
- **Player portraits (`headshots.R` / `headshots.py`).** The player-centric bar charts (playoff players, trade/waiver performance) hang each row's Sleeper headshot just left of x=0, keyed off the `player_id` the metric now carries. Sleeper hosts one photo per id at `https://sleepercdn.com/content/nfl/players/<id>.jpg`; a **team defense has no face**, so a `DEF` (or a short all-letter id like `SEA`) falls back to the team logo at `.../images/team_logos/nfl/<abbr>.png`. Everything here is **best-effort and never blocks rendering**: a fetch that 403s (a player with no photo answers 403 with an HTML page, *not* 404, so insist on an `image/*` content-type, don't trust the status), times out, or hits no network returns `NULL`/`None` and the row keeps its plain text label; misses are cached so a 20-player chart doesn't re-attempt 20 dead downloads per redraw. Downloads cache to `~/.cache/sleepermetrics/headshots` (on Windows resolve `USERPROFILE`, not `~`, which R expands to Documents/; both instances must share one cache). **`SLEEPERMETRICS_NO_IMAGES=1` turns portraits off entirely** and is set by both test suites so the tests stay network-free, which also means charts you render in a shell that has it exported come out portrait-less (that is the flag, not a bug). Sleeper serves a PNG from a `.jpg` url often enough that the loader **sniffs magic bytes** rather than trusting the extension. Charts stay parity-checked because portraits are a pure overlay (no metric numbers change), and the exporters now diff `player_id` too.
- **Missing values must be scrubbed at the template boundary (`records()`, app.py).** Every template guards a missing value with `is not none` or `or "N/A"`, and **pandas NaN defeats both**: it is neither `None` nor falsey, so the guard sails through and the cell renders the literal `nan`, or `+nan` once a format string has been applied. This is not a template bug and cannot be fixed template-side one cell at a time; it bit on the playoff summary's champion, the weekly scoreboard's opponent/result/margin, and the manager avatars, each of which *already had* a correct-looking fallback that could never fire. Hand template rows through **`records(df)`** (`to_dict("records")` + NaN/NaT/`pd.NA` to `None`) rather than calling `to_dict` directly, and the guards mean what they read as. The sweep that finds regressions is rendering every tab × season and grepping the HTML for `>nan<`; do that rather than reasoning about which columns can go null.
- **A metric that can be empty needs *wording*, not just a non-null value.** "No value" usually means something specific, and the honest label is rarely blank: a playoff team with no elimination round is the **Champion** (or *Still alive* in an unresolved bracket), and a team with no opponent that week played **no game** (a bye or an eliminated team in a playoff week) rather than having an unreadable result. `sl_playoff_summary()`/`playoff_summary()` therefore return a never-null `outcome` and the column is headed **Outcome**, not "Eliminated in".
- **Elimination is the last loss in the TITLE bracket, not the last loss overall.** Consolation games are played *after* a team is already out, so ranking by them overstates the run; five teams across 2022-24 were reported a round or two deeper than they actually went (2022 diogenesthecat read "Lost in Round 3" for a consolation game after a Round 2 exit). `playoff_summary` filters to `bracket == "title"` and falls back to any loss only for a team that never appears there.
- **Consolation bracket vs losers bracket (`sm.consolation_bracket()`).**  Two distinct postseason sub-competitions, renamed 2026-08 (was `toilet_bowl()` -> `consolation_bracket()`; the old in-bracket `bracket == "consolation"` tag -> `bracket == "losers"`).  **Consolation bracket** = the teams that **missed the main playoffs entirely**, and the games they played once the postseason started -- ordinary Sleeper matchups that never appear in the bracket config, so reading the config alone reports no consolation bracket for such a season (2025: sparky1335 beat rezzu in wk15, so rezzu finished last).  **Losers bracket** = eliminated **finalists** playing on to settle placement (3rd, 5th, ...); `_tag_bracket()` marks those `bracket == "losers"` and `scope_frame(d, "losers")` filters to them.  The config's losers-bracket placement games are between teams that **made** the playoffs, so the loser of the last one is often a strong team (2022: diogenesthecat, who finished **first** in the regular season) -- deriving last place from them is wrong; that comes from the consolation bracket.  `consolation_bracket()` returns `winner` and `last`: **`winner` is the actual winner of the final consolation game** (2026-08 redefine -- it used to return the LOSER, an old "win the toilet bowl = you're the worst" in-joke; the UI now labels it "Consolation bracket champion").  **`last` ("Biggest loser") is the team FIRST OUT of the consolation field**, not the loser of the final game (that team went deepest on the losers' side, nearer mid-table): it resolves Sleeper's `sleeper_losers_bracket()` and takes the loser of the highest-`p` placement game (`p == 5` -> 5th/6th, whose loser is dead last), falling back to the missed team whose consolation run ended earliest (smallest last-week-played, tie-broken by worse regular-season finish), then to the worst regular-season finish and *labelling* that it did; a season where every team reached the playoffs has no consolation bracket and says so.  Corroboration to re-run if touched: in every season that has one, the first-out team is also the worst regular-season finisher.  Its drill-down is a **matchup** drill: each row is the game, expanding to both **lineups** (from `pl_wk`, ordered through `assign_slots`, since a consolation-bracket game is a plain Sleeper matchup and never touches the bracket engine's `players`); the check that the lineup extraction is right is that the starters sum to the team's score.  Sleeper's own `/losers_bracket` endpoint (`sleeper_losers_bracket()`, `plot_playoff_bracket(variant="consolation")` -- note the internal `variant` string kept its old value) is a THIRD thing: the tree that structures the consolation field for a chart; it is drawn by `plot_consolation_bracket()` when it resolves, else a flat week-column fallback.

- **Bracket chart: nothing may sit between the title and the axes (`plot_playoff_bracket`).** The round names are **top-axis tick labels**, so a subtitle drawn at `y≈1.02` renders straight through them; this shipped overlapping and got worse when a second clause was added. There is no subtitle band on this chart: the champion rides **in the title**, and explanatory text goes to the **bottom** via `fig.text` + `tight_layout(rect=...)` (same rule the matrix charts already follow). A bye/idle node shows the team's real weekly score **in parentheses** rather than a dash (`reference_scores(s)` supplies `{(manager, week): points}` and `_ref_label()` sums a multi-week round) because a dash reads as missing data when the number is sitting in the season. Parenthesised precisely because it decides nothing: the team advanced on the bye, not on those points. Python/webapp only; R's `sl_plot_playoff_bracket` is unchanged.

- **Bracket chart layout: round-fan tree for DEFAULT Sleeper brackets, byte-identical flat layout for custom ones (`plot_playoff_bracket`, 2026-08 redesign).** The redesign is **gated on `placements`** (a default Sleeper bracket carries `p`-tagged placement nodes; a hand-authored config like DDBM 2025 does not).  For a default bracket: pass 1 spaces round `cx`'s games by `PAIR_STEP * TREE_FAN**cx` (`TREE_FAN = 1.55`, capped `4.0*PAIR_STEP`), then the final round's title game is pulled onto its feeder-mean (apex), giving a fanned tree; a custom bracket keeps flat `PAIR_STEP` and renders exactly as before ("leave DDBM 2025 alone").  Card constants moved (`CARD_GAP` 0.50->0.62, `LANE` 0.56->0.78, `_MIN_SPAN` 4.3->5.4) for wider spacing.  **The `result == "W"` card floats to the top of EVERY terminal matchup** (`_terminal_mids = {_final_cfg} | placements`), not just the championship final.  **Finishing-place chips** sit on the upper card's right edge of a terminal matchup (winner takes `place`, loser `place+1`); palette is SATURATED (`_PLACE_CHIP`: 1 gold `#f1c40f` / 2 blue `#4f86c6` / 3 bronze `#c9752e` / 4+ violet `#8f6fc0`), NOT a metal-grey ramp (a "silver" 2nd read as the neutral bye card); chip text is a dark/white LITERAL (card fills are always light, dark-mode rule).  **Placement labels** ("Placement game" / "Nth-place game", from `_place_tag`) are HORIZONTAL, left-aligned to the card's left edge, just above the matchup's top card (a rotated label in the connector gutter was unreadable).  **Loser connectors** (`LOSS_LINE = "#d99b9b"`, reddish dashed, `zorder=0`) draw only when a `result in ("L","T")` team reappears in the very next round.  **Round headers are two-line**: round name + `"Week 15"` / `"Weeks 17-18"` (from `p.results`' `weeks` column, scalar or list).  Higher placements float to the TOP of the vertical ordering (`unit_place_rank`: title path 0, placement games by `p`, untagged consolation 1000), default brackets only.  Python/webapp only.

- **The playoffs `scope` control is analytics-only, and dies quietly on a bracket with no consolation.** "Count which games?" filters `p.results` on the `bracket` column (`title`/`consolation`). It **never filtered the bracket graphic**, which always draws every game. Two traps behind "it doesn't work": (1) on a season whose bracket is entirely title games (2025), `title` and `all` return the **identical frame** and the rendered PNGs differ only by the caption text, while `consolation` returns **zero rows** and both charts fall back to the same no-data placeholder, so the control is hidden when `bracket == "consolation"` matches nothing, rather than offering three options two of which are the same; (2) it **cannot** reach the consolation bracket, whose games are plain Sleeper matchups that never enter the bracket engine and so carry no `bracket` tag at all; that is a separate section, not a fourth scope. **The standalone "Playoff analytics" section is GONE (2026-08 reorg, supersedes the "it belongs beside Playoff analytics" framing this bullet used to end on)**: the scope control plus its two charts moved INSIDE Postseason results, above the standings table. Final section order top to bottom is Insights tiles, Bracket, Postseason results (standings table, then the scope control, then the two charts), the Games log (a lazy-loaded, round-grouped scoreboard-to-lineups drilldown, replacing the old bracket walk/per-matchup chart/postseason-weeks table), then the scoring chart. - **The Games log's round groups name their matchups by SEED, split across `label` (the bolded title) and `blurb` (bye + pick callouts) (`game_log()`, `playoffs.py`).** `label` is the round's display name plus its games in parens, e.g. `"Round 1 (#5 vs #8, #6 vs #7)"` (each `#N` is that team's final regular-season standing, `season_rank`; an unresolved side reads `TBD` rather than being dropped) -- built by `_round_title`, generalized from the round's own shape rather than its display name, since names vary by league/season (2025: "Round 1 (seeds 5-8)"; 2022: plain "Round 1") the same way the splice chart's round-depth coloring already had to sidestep display names. **`_round_title` strips any existing `"(...)"` suffix off the config's own display name before appending the seeded matchups** (this league's "Round 1 (seeds 5-8)" renders as just `"Round 1 (#5 vs #8, #6 vs #7)"`, not a double-parenthesized "Round 1 (seeds 5-8) (#5 vs #8, ...)"), since that suffix is now redundant with the matchups appended right after it, and with the pick round's own blurb sentence below. Only the TITLE strips it -- `_pick_blurb` still reads the UNSTRIPPED name (passed to both functions from the same `base_name`) for its own "pick" detection. `blurb` (rendered under the heading in `_playoff_round.html`, also carries an `is_final` flag on the group) never restates the matchups already in `label`; it's the bye callout (`_bye_blurb`, e.g. `"Seeds 1-4 on a bye."`; its `_seed_ranges` helper collapses consecutive seeds into a range rather than listing every one, and a bye whose seed can't be resolved is still counted ("N more teams") rather than silently dropped), plus for a "choose-your-opponent" round a pick callout (`_pick_blurb`). **Pick-round detection reads the round's own display name for the substring "pick"** (this league's 2025 custom bracket literally names them "Round 2 (seeds 3-4 pick)"/"Round 3 (seeds 1-2 pick)") rather than inventing a second structured config field -- the config's own `_pick` key (e.g. `"seed 3 SearingShadow picked xPsyD"`) is a human-readable comment only, never read by the engine. Within a detected pick round, `_pick_blurb` derives the chooser per game as the LOWER `season_rank` number (the higher seed) with no dependency on the `_pick` comment, orders games chooser-seed-ascending, and phrases every pick but the last as a real choice ("Seed 3 chooses #8") and the last as its automatic leftover ("leaving seed 4 to take on #7") rather than repeating "chooses" for a seed with nothing left to pick from. The consolation-bracket group's `blurb` is unrelated (no seed-matchup structure there) and keeps its own longer sentence explaining these are games between teams that missed the bracket entirely and naming who it eliminated to last place, mirroring `consolation_bracket()`'s own `last`/`basis` fields. Python/webapp only.

- **The regular season is split from the postseason at season assembly, in BOTH languages.** `sl_season`/`assemble_season` filter `team_wk`/`pl_wk`/`lineup` to weeks `1..playoff_week_start-1`, so every downstream metric (standings, luck, efficiency, all-play, power rank, career) is a *regular-season* metric without any of them special-casing anything. Filtering once, identically, in each language is what keeps parity; the exported values changed (939 → 874 records) and both sides moved together. Where a league runs its playoff outside Sleeper those weeks are phantom matchups nobody played: 2025 LuckyHarm read **16-1** against an actual **13-1**. The corroboration that this is right: `final_position` now reproduces **all eight** of the 2025 bracket's stored seeds, where the all-weeks version matched only four. `team_wk_all`/`pl_wk_all`/`last_week_all` keep every scored week for the postseason features, and **`consolation_bracket`, `reference_scores`, `_lineup_of` and `playoff_replay` must read those**; on the scoped frames they silently find nothing (R's `sl_playoff_replay` returned all-null until it was pointed at `pl_wk_all`). `last_week` is now the last *regular-season* week: it is the default for "the latest week" everywhere, and leaving it at `last_scored_leg` indexed an empty frame. - **Chart form follows the data's job; the Weekly tab is the worked example.** Three bar charts in a row got replaced by three different forms: a **dumbbell** per matchup (bars hide *who played whom*; the line between the dots is the margin), a **PF-vs-PA scatter split by the tie diagonal** ("was I beaten or unlucky?" is a two-number question no single-value chart can answer; below the line you won, colour is all-play merit), and a **bump chart** for the race through week N. - **Scatter labels need a real collision solver, and it must run AFTER `_finish` (`_place_labels`).** A fixed offset works until two teams land in the same corner. `_place_labels` tries ten candidate offsets per point and keeps the first whose *rendered* box clears every placed label and every marker, densest points first; extents are **measured**, not estimated from string length. It must be called after `_finish`, which runs `tight_layout()`; geometry solved before that is stale by the time it draws. Fixed artists (the "lost"/"won" zone captions) have to be passed in via `avoid=`, or the solver treats their space as free. The check to re-run is rendering every week × season and counting text-vs-text and text-vs-marker overlaps from the real extents: it went 25 → 0 across 56 weeks, and eyeballing one week had missed all of them. `plot_pf_pa` and `plot_manager_profile` used to skip this solver entirely (a fixed `xytext` offset, same bug in miniature; avatars/labels overlapped in a tight cluster on real 2025 DDBM data), fixed by capturing `_point_avatars()`'s own return, calling `_finish` first, then `_place_labels(..., avoid=(*avatars, *corners))`. Same collision recurred twice more (2026-08): `plot_draft_grades_value`'s rows are sorted by `points` ascending, so its fixed lower-right legend sat on the bottom row's own label every time, and `plot_clutch`'s did the same on its scatter; both were dropped for the identical "subtitle already states the encoding" reason rather than fixed with a new position; this shape (a fixed-corner legend colliding with real data, subtitle-redundant either way) is now an established pattern in this codebase, not a one-off.
- **A week is a set of GAMES, not a list of teams (`metrics.week_matchups`).** The weekly scoreboard groups by matchup and drills into both lineups in slot order, each side carrying optimal/efficiency/bench and the single legal same-position swap that cost most. `flips` (that swap alone turning a loss into a win) **must agree with `bench_regrets.flipped`**; that is the check, and it caught the real bug: `team_wk` carries `points` and `pa` but **no `margin` column**, so reading `r.get("margin")` made every game look undecided and found 0 flips league-wide instead of 24. - **Dark-mode charts (Python web app).** The FastAPI dashboard's charts are server-rendered matplotlib PNGs, so they can't read the viewer's colour scheme themselves; the *structural* palette (surface, text, grid, spines, marker edges, neutral fills) is a switchable token dict `plots.T`, selected by `plots.set_chart_theme("light"|"dark")` which also syncs matplotlib rcParams for the implicit colours (legend/tick text). - **Draft gems/busts/steals are POSITION-scoped, and `steal`/`pos_steal`/`pos_adj` answer three different questions (`draft.py`).** `pos_pick_rank` (order taken within his own position) vs. `pos_value_rank` (rank within position by points the DRAFTING team banked) gives `steal`: team-realized value, scoped to the drafting roster only, so a player traded away mid-season reads near-zero however well he went on to score elsewhere; that's intentional (`steal` is "was this pick a good DECISION for the team that made it"), not a bug to "fix" with a was-he-dropped flag. `pos_pick_rank` vs. `pos_rank` (true leaguewide position finish, capped at how many players were actually drafted at that position, since an uncapped real-NFL universe made a deep position's bust dwarf an equally-deserved bust at a shallow one) gives `pos_steal`: the TRUE-value equivalent, immune to trades/drops. `pos_adj` is a third, independent read: `total` (true season points) minus **replacement level** at the position (`_replacement_level`, the Nth-ranked real player leaguewide, N sized to the league's own starter slots, not the mean of the top N, which an elite outlier skews upward). **`mixed`** flags `pos_steal`/`pos_adj` disagreeing in sign, a rank-based read and a magnitude-based read of the same replacement comparison telling different stories (good by one, bad by the other); deliberately NOT `steal` vs. `pos_steal` (an earlier version): `steal` isn't even a column shown on the table, and comparing it against `pos_steal` conflated two differently-sized comparison pools (drafted-only vs. the full real-NFL universe), which could flip the sign at IDENTICAL points and falsely flag a plain, undisputed bust (2025's Jerry Jeudy) as "mixed" with no real disagreement behind it.
- **`pos_pick_rank` is a visible column (Order, e.g. "RB5") since users read `pos_steal`/`+/-` against overall pick number by default, not position order.** 2025 real case that prompted this: McCaffrey (pick 1.09) looked like a smaller surprise than Taylor (pick 3.02) by raw draft slot, but McCaffrey was only the 5th RB taken (Barkley/Robinson/Gibbs/Henry went first) while Taylor was the 9th; `+/-` compares THAT position-relative order against position finish, never the overall pick, and was unreadable without the order itself on the row. For an UNDRAFTED player, `pos_pick_rank` used to be ONE SHARED CONSTANT for every player at a position (`drafted_n + 1`, e.g. every undrafted WR read "WR59"), which is fine as a `pos_steal` input but reads as a fabricated tie once shown as a column; fixed by individualizing it WITHIN the undrafted tier by true season `total` (best first, ties broken on `player_id`), still starting one worse than the last real pick. This shifts `pos_steal` for every undrafted player except whichever keeps rank 1 in its group (a real, accepted behavior change, not a side effect to avoid; verified it doesn't touch drafted players' `pos_steal` at all). The individualization logic now lives ONCE, in `_undrafted_pos_pick_ranks(board, ranks)`, called by both `undrafted_standouts()` (the main table) and `_pos_pick_ranks()` (the per-team drilldown); they used to reimplement this fallback independently, which is exactly the "compute a paired/derived figure twice and let them drift" shape that already bit once on `weeks`/`ppg` (see below) and had silently made the drilldown's `pos_steal` disagree with the same player's row on the main table.

Its lineup rows carry a new `swapped` flag (True on a started player the optimal lineup would drop, or an optimal pick that wasn't started) rendered with the same `.bench-impact` gold highlight the bench section's `would_start`/`was_started` flags already use, so a swap reads consistently across both the Started and Optimal tables. `bench`'s `would_start` here is deliberately NARROWER than `week_matchups()`'s own version of the same flag (any bench player individually beating the worst same-position starter): with the Optimal table sitting right beside it, that looser rule could gold-highlight a bench player the optimal lineup never actually picked (real case: LuckyHarm wk6 2025, two bench WRs each individually beat the starter but only one had an open slot); here it's `player_id in opt_ids`, true only for a bench player who IS one of the optimal lineup's actual picks. `week_matchups()`'s own `would_start` was tightened to the identical `opt_ids`-based rule for the same reason.

- **Efficiency-axis floor for Started-vs-Optimal charts is centralized in one function, `_eff_axis_floor(eff)` (plots.py): `max(int(float(eff.min()) // 10 * 10), 0)`.** The floor is the lowest REAL value in whatever series it's handed, rounded down to the nearest 10, never a fixed constant (an earlier `min(50, ...)` was backwards: `min()` keeps the SMALLER value, so it forced the floor down to 50 even when the real low was higher, e.g. stranding a season whose worst week was 77% in the top ~40% of its own axis) and never average-derived (a season-mean-based version was tried and rejected the same way). Top is always a fixed `102` (not 100) so a real 100%-efficiency week's marker never sits flush on the axis edge; ticks via `MultipleLocator(10)`. **The two callers pass DIFFERENT series, and this is a deliberate divergence, not a bug**: `plot_season_optimal` (league-wide average, one line) stays self-scoped, its own per-week average series, floor independent of every other chart. `plot_mgr_optimal` (per-manager chart) instead passes the WHOLE LEAGUE's efficiency series (every manager, every week, `through_week`-scoped when capped) so every per-manager chart shares ONE floor and stays comparable side by side when flipped between managers; this supersedes an earlier state where both charts were purely self-scoped per-chart. Don't reintroduce a hardcoded floor or a duplicate formula in either caller; change the rule (or which series gets passed in) at the call site, never inside `_eff_axis_floor` itself.
- **`_highlight_eff_extremes(ax2, w, eff)` (plots.py) marks the best/worst week on a Started-vs-Optimal trend line, shared by `plot_mgr_optimal`/`plot_season_optimal`.** Lowest week always gets a labelled dot (blue, `#1f77b4`). Highest week gets a labelled dot too, UNLESS it's a real 100% (efficiency is capped there), in which case it draws a gold star (`#f1c40f`) with no value label, since "100%" is already stated by the axis top plus tick. If the best and worst week are the same single week, the low styling wins (a star on a lone below-100% week would misrepresent it as flawless). Colors are deliberately NOT the chart's own green/red bar palette; gold/blue read as a distinct layer instead of blending into the bars underneath; each marker has a thick white ring for contrast against whatever bar color it lands on, and each value label sits in a `T["bg"]`-colored rounded pill (same convention `_place_labels` uses) rather than bare colored text, since plain text in these colors was still hard to read against the green bar fill and grid lines. Skips silently under 2 points.
- **New chart `plot_playoff_players_splice` is now the PRODUCTION "Best Playoff Players" chart on the Playoffs tab (replacing `plot_playoff_players` there; see the corrected scope-control bullet above).** Instead of one solid bar per player, each player's total-points bar is cut into one SEGMENT PER PLAYOFF GAME (reading `playoff_performances()`, the row-per-player-week grain `playoff_players()` itself aggregates from), ordered chronologically (earliest career playoff game first, left to right) so a late hot streak or an early quiet stretch shows as a shape, not just an implied total; since this is a CAREER leaderboard, a player's games can span multiple seasons. Color is GAME SLOT (1st game, 2nd, 3rd…), not position; it reuses `_MANAGER_HUES` purely as an ordered categorical set keyed by slot index, the same "index by position in a sequence, not by manager identity" trick `plot_trade_single_contribution` already established for its own per-player segments (see that function for the precedent); position moves into the row's text label instead, and there's no swatch legend since a "game 1/2/3…" key would need as many entries as the deepest career run. The label also carries a `POS #rank` badge; since this is a career chart, a player can have scored in more than one season, so "the" rank is ambiguous; it resolves to that player's MOST RECENT scoring season's position rank, which is why this function (and its caller in app.py) now takes a `seasons: dict` param (`{season_str: Season}`, the same shape `plot_clutch` already takes); a season key with no matching `Season`, or no rank for that player, degrades to no badge rather than failing the chart.
