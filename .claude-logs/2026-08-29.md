## Session continuation (afternoon): drilldown gap-column regression

### Symptom
User: "some columns/column headers are now cutoff and not fully displayed"
in the drilldown areas. Prior session's last screenshot
(`Screenshot 2026-08-29 122909.png`) shows the Rivalries drilldown with all
real columns bunched hard left, a huge empty band, and the "MARGIN" header
clipped to "MARG...". Earlier screenshots (`114555`, `121608`) showed the
same table spread evenly with no clipping -- so the final "header-width
factor + padding bump" change from the prior session had regressed it.

### Root cause
`_colgroup` rendered each group-separator spacer as a bare, width-less
`<col>`. The design intent was "the spacer absorbs leftover width so real
columns stay pinned to their measured content". But once `_content_widths`
made the real columns genuinely content-tight (Rivalries drill sums to
~50ch against a ~130ch panel), the 2 bare spacers were the ONLY columns
`table-layout:fixed` could funnel the ~80ch of leftover into -- so each
spacer ballooned to ~40ch, taking ~60% of the table and squeezing every
real column (and clipping the "MARGIN" header inside its now-too-narrow
10.5ch box + 10px padding + `overflow:hidden`).

### Fix (per user choice "Bounded spacers, keep grouping")
- New module const `report._GAP_CH = 3.0`.
- `_spaced_cols` now stores `_GAP_CH` (not 0) at each gap position in
  `widths2`.
- `_colgroup` now emits an explicit `width:Nch` on EVERY `<col>` -- real and
  spacer alike -- so all columns join the proportional pool
  `table-layout:fixed` distributes the `width:100%` leftover across. Real
  columns keep their relative sizing; spacers stay a modest ~3ch-scaled gap
  instead of eating the table.
- Docstrings on `_spaced_cols` / `_colgroup` and the `_CSS` + `style.css`
  `.gap-col` comment blocks rewritten to describe the bounded-spacer design
  and why the width-less version failed.
- `test_report_spaced_cols_inserts_real_gap_columns` updated: now asserts
  each gap `<col>` carries `_GAP_CH` and `widths2` holds `_GAP_CH` at gap
  positions (was asserting a bare `<col>`).

### Follow-up: drilldown Player-name content cutoff

`Screenshot 2026-08-29 125807.png` ("Where the points came from", RB
drilldown): the Player column truncated every name ("Jonathan Taylor...",
"Travis Etienne R...") with the POS #rank badge dropped entirely, while the

Two compounding causes:
1. `_content_widths` measured Player cells via `_text_len`, which strips ALL
   markup -- so the ~20px portrait disc + 6px margin and the `.posrank`

2. The header factor `round(h*1.35)+2.5` over-inflated every multi-word
   numeric header ("Share of pos" -> 18.5ch, "Starts" -> 10.5ch for 2-char
   data), pushing the table's measured width past the panel; under
   `table-layout:fixed` every column then scales DOWN to fit and the widest
   text column (Player) is the one that visibly clips.

Fix:
- New `report._cell_width(html)` = `_text_len` + 4ch per `.pface`/`.face`
  portrait + 1.5ch per `.posrank` badge. `_content_widths` now measures
  data cells with it (headers still use `_text_len`).
- Header factor softened from `round(h*1.35)+2.5` to `h*1.22 + 2` (models
  `.06em` letter-spacing + uppercase, without the runaway flat add).
  "Share of pos" 18.5 -> 16.64ch, "Starts" 10.5 -> 9.32ch, "Pts" 6.5 ->
  5.66ch; Player 22.5 -> 24ch raw. Table now measures ~102ch against a
  ~150ch+ panel, so it scales UP and Player lands ~36ch (fits any name +
  badge + portrait).
- `test_report_content_widths_measures_actual_text_not_markup` updated for
